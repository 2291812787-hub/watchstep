# 催步 WatchStep

一个只做一件事的手表 app：**每 30 分钟走够 200 步，走不够就一直催。**

纯本地运行，不联网、不上传、不需要 iPhone 在旁边。手表蜂窝开着或关着都一样工作。

---

## 一、这个 app 要解决什么

目标不是"提醒你一下"，是**密到无法忽略**：

1. 以「上次走够的那一刻」为锚点，30 分钟内没走够 200 步 → 开始震。
2. 开始震之后，每 5 分钟再震一次，措辞升级，**直到你走够为止**。
3. 一旦某个时刻累计步数达到 200 → 立刻停、锚点归零、重新开始算下一个 30 分钟。

走够了就完全不打扰，走不够就烦到你起来。

---

## 二、设计上的三条不变量（为什么它不会像别的 app 那样失灵）

那个 200 元/年的同类 app 有个众所周知的 bug：**后台已经把计时清零了，前台显示也是清零的，但时间一到照样响**。根因是它把状态存了三份——前台计时器、后台计时器、系统托盘里预排的本地通知——三者互相脱钩，而预排进系统的通知是不可撤销的。

本项目的做法：

**1. 只有一个时间锚点，没有第二个计时器**

```
anchor      = 上次走够的时刻           ← UserDefaults 里唯一一条时间
deadline    = anchor + 30 分钟          ← 任何时刻现算，从不存储
```

没有"前台 timer"和"后台 timer"之分。任何地方需要知道还剩多久，都从 `anchor` 现算。**只有一个状态，就不可能分裂成两套。**

**2. 判断不需要保活，只有震动需要**

`CMPedometer` 是系统级记账：app 被挂起、被强杀、手表重启，都没关系。之后用
`queryPedometerData(from:to:)` 能把整段窗口的步数**完整取回**（可回溯数天）。

所以：

| 需要什么 | 要不要 app 活着 |
|---|---|
| 知道这 30 分钟走了多少步 | **不需要** |
| 准点震你 | 需要 |

这是和那个 app 最大的区别——它靠保活来维持计时，而**计时本身根本不需要保活**，白耗电。

**3. 系统里永远最多只有一条待发通知，且它从最新状态派生**

每次判定之后（不论结果如何）都：

```
removeAllPendingNotificationRequests()
按最新 deadline 重排一条
```

任何一次"醒来"——抬腕点开、扩展会话启动、后台刷新——都先跑一次同样的判定函数，把内存状态和锚点对齐。**预排和对账是同一个函数，物理上不可能不一致。**

## 三、代码结构

```
Sources/
  WatchStepCore/            纯逻辑，不依赖 WatchKit，可在 Linux 跑测试
    Config.swift              阈值 / 时段 / 开关
    AnchorStore.swift         单锚点读写（唯一状态）
    RuleEngine.swift          唯一判定函数，纯函数
  WatchStepWatch/           watchOS app
    WatchStepApp.swift        入口 + 后台任务处理
    Core/
      WatchEngine.swift         主循环：判定 → 震动 → 重排通知
      StepReader.swift          CMPedometer 采样 + 历史查询缓存
      NotificationPlanner.swift 兜底通知的单条重排与对账
      ExtendedSessionManager.swift 分段延长会话（可撤销误报的关键）
      WatchBackgroundScheduler.swift 后台刷新排期
    UI/
      ContentView.swift         主界面
      SettingsView.swift        阈值 / 时段
      SelfCheckView.swift       自检（验收用）
  WatchStep/                iOS 空壳（安装容器，不做任何事）
Tests/WatchStepCoreTests/  19 个测试，对应下面的验收标准
```

## 四、验收标准（测试逐条对应）

| # | 标准 | 测试 |
|---|---|---|
| 1 | 走够 200 步 → 归零，不震 | `testReachTargetResets` |
| 2 | 静坐 30 分钟 → 震 | `testSilentThirtyMinutesAlarms` |
| 3 | 静坐 40 分钟 → 震两次以上 | `testAlarmRepeatsEveryFiveMinutes` |
| 4 | 静坐 35 分钟后走 200 步 → 立刻停，且无残留通知 | `testResetCancelsPendingChain` |
| 5 | 杀掉 app 再打开，数字与真实一致 | `testAnchorSurvivesRelaunch` |
| 6 | 走够立刻归零，不产生误报 | `testFullCycleSimulation` |

第 4、5 条正是那个 200 元 app 的 bug，这两条过了才算及格。

## 五、构建与安装

**不需要 Mac。** GitHub Actions 在云端编译（`macos-latest`），产出未签名 IPA；
签名和安装在你自己的 Windows 上完成。

### CI 会做什么

- `逻辑测试`：ubuntu 容器里 `swift test`，跑 19 个测试
- `无签名编译`：macOS runner 上 XcodeGen 生成工程 → `xcodebuild build` → 打包 IPA
- 两个作业都会把日志和产物推回 `ci-test` / `ci-build` 分支（私有仓库读不到 Actions 日志，只能这么回传）

### 自签安装（7 天有效）

1. Windows 上装 **iLoader 手表版**（原版不支持 watch 签名）
2. 用**小号 Apple ID** 登录（不要用主力账号——这是第三方闭源工具）
3. 插上那台手表专用 iPhone，信任此电脑
4. 用 `ci-build` 分支里的 `WatchStep.ipa` 安装

**两个已知的坑（都踩过）：**

- **iPhone 端和手表端的签名配置必须一致**（都是 dev 或都是 distribution）。
  不一致会被判定为降级，手表会**自动卸载**这个 app，而且卸载后重装不上。
- 手表 app 装不上时：先卸掉 iPhone 上那份，保持手表和 iPhone 连接，
  用电脑**同时**安装。

### 7 天到期

免费签名到期后 app 会**静默失效**——不启动、不提醒、不报错。这是提醒工具最糟的
失效方式。所以：

> **每 6 天必须重刷一次。** 到期前一天务必提醒自己。

这条不是可选项。如果连续两周都没重刷，这个工具就等于不存在。

## 六、已知限制

1. **段间可能漏一次提醒。** 挂起期间撤销不了预排的通知（这是它的物理根源，任何
   app 都逃不掉，只能靠保活消除）。所以白天要不要开分段会话，是「电池」和「绝不
   误报」的二选一。
2. **延长会话连续开启可能被系统限流。** 每段 1 小时上限是文档明确的，但"到期后
   能不能立刻续下一段"没有保证。真机戴一天才知道。
3. **表盘不显示实时步数。** 第三方做不到（系统只渲染日期差，不渲染数据）。表盘只
   放三档状态：✓ / ⚠ / 🔴。会自己走的秒数只在催命弹窗里出现——那里是准的。
4. **震动需要 app 活着。** 会话断了就退化成预排本地通知，仍会响，但时间不如直接
   haptic 精确。

---

## 七、电量

| 档 | 能准点震 | 走够了能撤销误报 | 耗电 |
|---|---|---|---|
| 挂起 + 预排通知 | ✅ | ❌ | ~0 |
| 分段延长会话（推荐） | ✅ | ✅ | 1–2%/小时 |
| workout session | ✅ | ✅ | 3–6%/小时 |

推荐只在"催命时段"（如 08:00–22:00）开分段会话，晚上自动关。按 1.5%/h 算，一天
约 10% 电池——这是准点且不误报的代价。
