# 催步 WatchStep

一个只在 Apple Watch 上跑的小工具：**每 30 分钟必须走够 200 步，否则每 5 分钟震你一次，一直催到你走为止。**

不联云、不联小米、不联 iPhone、不需要 Mac。判断和震动全在手表本地。

---

## 为什么重写而不是买现成的

市面上那个同类 app 有个结构性 bug：状态存了三份（前台计时器 / 后台计时器 / 系统托盘里预排的通知），
于是"走够了、里面已经归零、到点照样响"。

这个版本从设计上就没有第二份状态：

```
唯一状态 = anchor（上一次走够的时刻）
还剩多久  = anchor + 30min - now      ← 永远现算，不存
判定      = 走够？ → 归零
            窗口满？ → 催
            其余     → 静默
```

前台 tick、后台唤醒、开机、用户点按钮，**全部调同一个 `RuleEngine.decide`**。物理上不可能分裂成两套逻辑。

另一个关键点：**计步不需要 app 活着。** `CMPedometer` 是系统账本，app 被强杀、手表重启之后
`queryPedometerData(from:to:)` 都能把这段时间的步数完整查回来。所以"判断"永远不需要保活，
"震动"才需要 —— 这是同类 app 最大的浪费（靠保活维持计时，而计时根本不需要保活）。

---

## 三条硬约束（写在前面）

| 事实 | 后果 | 我们的应对 |
|---|---|---|
| 挂起后 haptic 发不出去 | 走够了没法立刻停催 | 生效时段内开 `WKExtendedRuntimeSession`，1–2%/小时 |
| 预排的本地通知**撤不回来** | 可能有一次误报 | 通知正文不写死分钟数；每次醒来先清空再按锚点重排，系统里永远最多一条 |
| 复杂功能刷新预算约 4 次/小时 | 表盘不能实时 | 表盘只显示三档状态（正常/快到了/该动了），**不显示活步数** |

误报是物理成本，任何 app 都逃不掉 —— 只能靠"会话活着"把窗口压到最小。

## 结构

```
Sources/WatchStepCore/       纯逻辑，无 WatchKit 依赖 → 能在 Linux 上跑测试
  Config.swift                 阈值、时段
  AnchorStore.swift            唯一状态源（anchor）
  RuleEngine.swift             唯一判定入口
Sources/WatchStepWatch/      手表 App
  Core/StepReader.swift        CMPedometer 封装（带缓存，避免打爆数据库）
  Core/NotificationPlanner.swift  兜底通知 + 对账
  Core/ExtendedSessionManager.swift 延长会话，到期自动续
  Core/WatchEngine.swift       把上面串成一条链
  UI/                          主界面 / 设置 / 自检
Sources/WatchStep/           iOS 壳（只是容器，不做任何事）
Tests/WatchStepCoreTests/    验收标准 = 可执行测试
```

## 装到手表（长明 + iLoader 自签）

前提：免费 Apple ID 小号（**别用主力账号**）、一台 Windows、那台手表专用 iPhone、原装数据线。

1. iLoader 用**手表专用版**（原版不签 watch app）—— 2.3.1 有登录 503 bug，社区修过的版本或自己打个补丁
2. 取 CI 产出的**未签名产物**，用 iLoader 签名
3. **关键坑**：iPhone 和手表两侧必须用**同一个签名配置**。一边 dev build 一边 customer build 会被判降级，
   手表会在一段时间后**自动卸载这个 app**（这不是断连的锅）
4. 安装时：先卸掉 iPhone 上那份 → 保持手表和 iPhone 连着 → 用电脑同时装 → 记得在手表上信任电脑
5. 每 7 天重刷一次（免费签名有效期）。到期是**静默死亡**，所以要靠外部提醒

## 验收标准（做完了拿这个逐条对）

1. 走够 200 步 → 归零，不震
2. 静坐 30 分钟 → 震
3. 静坐 40 分钟 → 震两次以上（5 分钟一次，不吞）
4. 静坐 35 分钟后起身走 200 步 → 立刻停催，**系统里没有残留待发通知**
5. 强制挂起再打开 → 数字和实际一致，**不会出现"里面归零、外面还在倒计时"**
6. 当日账每一项对得上
7. 戴一整天，电量消耗记录在案
8. 把 app 从后台彻底杀掉，静坐 40 分钟再开 → 时间一致，该震的一次不少
9. 手表开飞行模式 → 一切照常
10. 表盘只允许三档状态，任何时刻不允许出现"走错的数字"

第 4、5、8 条就是那个 200 块 app 的 bug。这三条过了才能说比它强。

`swift test` 覆盖 1–5 的判定部分；剩下的必须在真机上验。

## 已知未验证项

- **`WKExtendedRuntimeSession` 连续续期可能被限流**。文档允许每段 1 小时，没说能不能无缝续。
  实测被拒时会退避到 2 分钟再试；如果一直续不上，就退化成"段间靠预排通知兜"（可能有一次误报）。
- 手表蜂窝待机时的耗电，需要真机实测。
